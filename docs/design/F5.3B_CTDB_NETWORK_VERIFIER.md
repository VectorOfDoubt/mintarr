# F5.3B — CTDB / AccurateRip network verifier design

> **Type:** Design
> **Status:** Proposed
> **Owner:** Mintarr maintainers
> **Related:** [F5.3 CD-rip evidence lane](F5.3_CD_RIP_EVIDENCE_LANE.md), [Quality stack roadmap §5.4](QUALITY_STACK_ROADMAP.md), [F4.5 optional verifier connectors](F4.5_OPTIONAL_VERIFIER_CONNECTORS.md), [ADR-0012 QC import-gate scope](../architecture/adr/0012-qc-import-gate-scope.md)

## 1. Problem

F5.3 (slices 1–4) parses a CD rip's **self-reported** evidence: the EAC/XLD log
says "AccurateRip confidence 12", and Mintarr trusts the log. That is useful but
forgeable — a log is plain text and can be edited to claim an accurate rip that
never happened.

An **independent online cross-check** against the AccurateRip and CTDB
(CUETools DB) databases turns self-reported claims into verified ones: it
confirms the disc exists in the database and, in its strongest form, that *this*
rip's audio checksums match the community-verified pressing. This is the
strongest authenticity signal available for the CD-rip lane.

This slice is **network-bound, CPU-bearing, and privacy-relevant**, so it is
intentionally separated from the local F5.3 work and kept **default-off**.

## 2. What the databases need

Both databases are keyed by a **disc identifier derived from the CD TOC** (track
count, per-track frame offsets, lead-out). Verification then compares **audio
checksums** computed from the decoded PCM:

| Database | Key | Strong proof requires |
|---|---|---|
| AccurateRip | AR disc IDs (FreeDB-style + two CRCs over the TOC) | per-track AR v1/v2 checksums over decoded PCM, with a pressing-offset search |
| CTDB (CUETools) | CTDB id (CRC of the TOC) | whole-disc CRC over decoded PCM (+ optional parity/recovery) |

Two consequences drive the slicing:

1. **The TOC must be reconstructed.** Mintarr has no physical disc — only ripped
   FLAC + a `.cue` + a log. Track offsets come from the `.cue` `INDEX` entries
   and the per-file FLAC sample counts (frames = samples / 588). Missing/garbled
   `.cue` or non-single-disc layouts mean the TOC cannot be built → the lane
   reports `skipped`, never a guess.
2. **Strong verification decodes audio.** Recomputing AR/CTDB checksums requires
   decoding every track's PCM — CPU-heavy and CD-rip-lane-only, never in the
   TIDAL/WEB hot path.

## 3. Decision: two sub-slices, lookup before recompute

### 3.1 Sub-slice A — disc-ID lookup (lighter, ships first)

Compute the disc IDs from the reconstructed TOC and **query** AccurateRip/CTDB
for that disc. Do **not** recompute local audio checksums yet.

- Confirms the disc is known to the DB and reports the community confidence
  (how many submitters ripped it accurately).
- Corroborates the log's plausibility and catches a fabricated/unknown disc.
- Cheap: TOC only (cue + FLAC sample counts), one cached HTTP query. No full
  audio decode.

This is the honest limit of a lookup: it proves *the disc exists and is
commonly ripped accurately*, not that *this copy is byte-correct*. Because of
that, **sub-slice A is advisory-only and carries no policy weight** — its
evidence is surfaced in the sidecar/dashboard but never changes the import
decision (see §5). The positive policy lift is earned only in sub-slice B, which
recomputes *this* rip's checksums from the audio.

### 3.2 Sub-slice B — checksum verification (heavier, follow-up)

Decode each track's PCM, compute AR v1/v2 (with offset search) and/or the CTDB
whole-disc CRC, and compare against the DB. This is the independent proof that
*this* rip matches the verified pressing — and the **only** sub-slice allowed to
affect the decision. Gated behind sub-slice A landing and its own performance
budget review.

## 4. Connector + sensor shape

A `ctdb` **VERIFIER connector** (F4.5 pattern), default-disabled:

- `ConnectorManifest(id="ctdb", kind=VERIFIER, default_enabled=False, required=False, docker_service=None, required_env=(), optional_env=("MINTARR_CTDB_ENABLED",), capabilities=("source_specific_proof","accuraterip_lookup","ctdb_lookup","network"), docs_url=…)`.
- Health: `disabled` when off; a cached reachability probe of the DB endpoint when on; `missing`/`degraded` on network failure — **never blocks**.

Emits a `ctdb` `SensorResult` (`source_specific_proof` / `source_specific`
stage), only when the connector is enabled **and** a TOC could be built:

Use only statuses already in the [sidecar contract](../specs/SIDECAR_FORMAT_v2.md)
(`pass`/`fail`/`warn`/`error`/`skipped`) — there is no `unavailable` status, so
network failures map to `skipped` with a `warning` severity:

| Situation | `status` | `severity` |
|---|---|---|
| Disabled, or no TOC could be built | `skipped` | `info` |
| Network timeout / DB unreachable | `skipped` | `warning` |
| Disc unknown to the DB | `skipped` | `info` |
| Disc found (lookup; sub-slice A) | `pass` | `info` |
| Sub-slice B: checksums match | `pass` | `none` |
| Sub-slice B: checksum mismatch | `warn` | `warning` |

- `severity` is always ≤ `warning`, **never `blocker`**.
- `evidence`: `{disc_id, ar_confidence, ctdb_confidence, db_total_submissions,
  matched (sub-slice B), source_db}` — disc IDs and counts only.

## 5. Policy mapping

No new policy rules: this reuses the **opt-in** scoring already wired in F5.3
slice 4 (`MINTARR_CD_RIP_SCORING`) and the §5.4 mapping. Only **sub-slice B**
(actual checksum recompute) may affect the decision; **sub-slice A (lookup) is
advisory-only** — a disc-presence/confidence lookup does not prove *this* copy
is correct, so it never moves the decision:

- **sub-slice A (lookup):** evidence only — surfaced in the sidecar/dashboard,
  **never** changes the decision (no positive lift, no downgrade);
- **sub-slice B verified** (checksums match) → positive evidence that can lift a
  borderline `REVIEW_REQUIRED` to `ACCEPT_PROVISIONAL`;
- **sub-slice B mismatch** with a complete TOC → `REVIEW_REQUIRED`;
- disc unknown / network failure / lookup-only → **no change** (absence of proof
  is not proof of a problem).

It never overrides a hard-gate `BLOCK` or identity `WRONG_ALBUM`, and never
blocks on its own — identical precedence to slice 4.

## 6. Network, performance, privacy

- **Default-off.** `MINTARR_CTDB_ENABLED=false`. The connector starts disabled
  and may be run in `dry_run` first ([F4.5](F4.5_OPTIONAL_VERIFIER_CONNECTORS.md)).
- **Lane-scoped.** `applies_to` excludes `tidal`/`web`; never in the TIDAL hot
  path ([quality stack §2.3 budgets](QUALITY_STACK_ROADMAP.md)).
- **Bounded.** Hard HTTP timeout, small retry budget, and a disc-ID-keyed cache
  so re-verification of the same disc is free. Failures degrade to a
  `skipped`/`warning` SensorResult (see §4) and never block.
- **Privacy / third-party disclosure (important, opt-in consent).** Enabling
  this sends a **disc fingerprint** (TOC-derived disc ID) to a third-party
  service (`db.cuetools.net` / AccurateRip). Disc IDs are non-identifying
  checksums of track offsets — not file paths, artist names, or account data —
  but a query still discloses *which disc* is being verified to an external
  party. This is why the feature is opt-in and documented as an outbound network
  call, consistent with how `MINTARR_NOTIFY_URLS` is treated. No audio is ever
  uploaded; only the computed disc ID / checksums.

## 7. Test plan

- TOC reconstruction from a `.cue` + FLAC sample counts → expected disc ID
  (fixture with known offsets); garbled/multi-disc cue → `skipped`.
- Lookup client: mocked HTTP returns found/not-found/low-confidence/timeout →
  correct `SensorResult` status per §4 (found→`pass`/`info`, timeout→
  `skipped`/`warning`, unknown→`skipped`/`info`); the network call is isolated
  behind one function so tests never hit the real DB.
- Default-off: connector disabled ⇒ no network call, no `ctdb` sensor emitted.
- **Sub-slice A is decision-neutral even with `MINTARR_CD_RIP_SCORING` on** — a
  lookup result never changes the decision. Only a sub-slice B checksum match /
  mismatch can, and it still never blocks.
- (Sub-slice B) checksum compute against a known-good decoded fixture.

## 8. Non-goals

- No CD ripping; Mintarr verifies completed rips, it does not create them.
- No audio upload — only disc IDs / checksums are sent.
- No new policy precedence; reuses §5.4 and the slice-4 opt-in flag.
- No blocking on the network lane: unknown disc or an unreachable DB is never a
  `BLOCK`.
- No tag writing or library reorganisation ([ADR-0008](../architecture/adr/0008-strategic-positioning.md) boundary).

## 9. Implementation slices

1. **TOC reconstruction + disc-ID computation** (pure, from cue + FLAC sample
   counts) + tests. No network.
2. **Lookup client** (sub-slice A): query AccurateRip/CTDB by disc ID, behind a
   timeout/cache/mockable seam; map to an **advisory** `ctdb` `SensorResult`
   (evidence only — no decision effect).
3. **Register the `ctdb` connector** (default-off) + emit the sensor when enabled
   and a TOC exists; dashboard visibility via the existing generic sensor render.
4. **Checksum verification** (sub-slice B): decode PCM, compute AR/CTDB
   checksums, compare; behind its own performance-budget review. This is the
   only sub-slice that feeds the (opt-in) decision per §5.
