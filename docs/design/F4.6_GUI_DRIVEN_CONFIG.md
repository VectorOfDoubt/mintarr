# F4.6 - GUI-Native Configuration (No-Env Setup)

> **Type:** Design document
> **Version:** 0.1 - 2026-06-16
> **Status:** Proposed - north star + staged path; no code yet
> **Related:** [F4.1 Static Connector Registry](F4.1_STATIC_CONNECTOR_REGISTRY.md), [F4.2 Integrations Dashboard](F4.2_INTEGRATIONS_DASHBOARD.md), [F4.3 Connector Config And Dry-Run](F4.3_CONNECTOR_CONFIG_DRY_RUN.md), [F4.4 Connector Install Guidance](F4.4_CONNECTOR_INSTALL_GUIDANCE.md), [MINTARR_MANAGED_SAB_QBIT_DOWNLOAD_CLIENT.md](MINTARR_MANAGED_SAB_QBIT_DOWNLOAD_CLIENT.md), [SECURITY_MODEL.md](../architecture/SECURITY_MODEL.md)

## 1. Goal and north star

**Destination: GUI-native configuration. Long-term, the GUI is the *only* config path.** A user spins up the container, opens the dashboard, and connects Lidarr / SAB / sources — and tells the lanes apart — entirely from inside the UI. No docker-compose env editing, no hand-wiring required to reach a working install.

Environment variables become a **transitional bootstrap** only: they seed initial config on first boot and remain a valid override during the transition, then are deprecated and removed once GUI-native config is complete. They are not a permanent parallel configuration surface.

This is the natural continuation of the F4 connector series: F4.1 made the registry, F4.2 surfaced status, F4.3 added operator-controlled *mode* (disabled/dry_run/import). F4.6 adds operator-controlled *connection settings* (URLs, credentials, paths) — the part still locked in env today.

## 2. Current state and gap

| Layer | Today | F4.6 target |
|---|---|---|
| Connection settings (URLs, keys, paths) | docker-compose env only | GUI-entered, stored, editable |
| Connector mode (disabled/dry_run/import) | GUI via `connector_config` (F4.3) | unchanged |
| Readiness | computed from env presence + reachability | computed from stored config + reachability |
| Lidarr-side wiring (add download client, pin indexers) | manual, in Lidarr's own UI | guided in-app (checklist / generated values), wiring stays in Lidarr |
| First-run experience | edit compose, restart | setup surface in the dashboard |

The Connectors page is presently a **status/diagnostics** surface, not a **setup** surface: `POST /dashboard/v1/connectors/<id>/config` changes only mode, never credentials. So the GUI is where you check *whether* setup worked, not where you *do* setup.

## 3. The hard constraint: "secrets never browser-visible"

[SECURITY_MODEL.md](../architecture/SECURITY_MODEL.md) and the roadmap's cross-cutting security row state **secrets are never browser-visible**. GUI-native config means secrets are *entered* via the browser — these are in tension and the tension must be resolved explicitly, not waved away.

**Resolution — write-only secret fields:**

- A secret (API key, password) can be **written** via the API (`POST`), but is **never returned** by any `GET`. The dashboard renders a masked placeholder (`••••••• set`) and a "replace" affordance, never the value.
- Stored **encrypted at rest** (see §5), never in plaintext in the state DB.
- Never logged; existing `download_backend.redact()` / `redact_params()` posture extends to any config echo.
- Readiness/validation responses report *presence and validity* of a secret, never the secret itself.

This keeps the principle intact: the browser can *set* a secret but can never *read one back*, and the secret is not at rest in the clear. "Never browser-visible" is preserved as "never browser-*readable*."

## 4. Config model

Extend the F4.3 persistence rather than inventing a parallel store. F4.3 added `connector_config(connector_id, mode, ...)`. F4.6 adds connection settings keyed the same way:

- **Non-secret settings** (URLs, paths, category names, numeric tunables): a `connector_settings` table (or JSON column on `connector_config`), one row/blob per connector, validated against the connector manifest's declared `required_env` / `optional_env` schema (reused as a field schema, not literally env).
- **Secret settings** (apikey, password): a separate `connector_secrets` store holding only ciphertext + a key reference (§5). Never co-located with non-secret config returned to the browser.

The connector manifest stays the single source of truth for *which* fields a connector needs (it already declares them as `required_env` / `optional_env`); F4.6 reinterprets that schema as a form definition.

## 5. Secret handling at rest

- Encrypt secret values with a key derived from a **container-level secret** (e.g. `MINTARR_SECRET_KEY` env / mounted key file), not from a browser-supplied value. This one bootstrap secret is the irreducible minimum that cannot itself be GUI-configured (chicken-and-egg) — document it as the single permitted config-secret.
- Use an authenticated symmetric scheme (e.g. Fernet/AES-GCM) so tampering is detectable.
- Rotation: changing the master key re-encrypts stored secrets; design a one-shot migration path.
- No Docker socket, no external secret manager dependency (consistent with the existing security posture).

## 6. Env transition and precedence

Staged deprecation, not a hard cutover:

1. **Bootstrap import:** on first boot, if stored config is empty and env is present, import env values into stored config (secrets encrypted). One-time, logged, idempotent.
2. **Precedence during transition:** env, when set, overrides stored config (so existing installs keep working unchanged) — but the dashboard shows "managed by env" and points the operator at the GUI field. This is the *only* phase where two surfaces coexist.
3. **GUI-primary:** once a setting is GUI-editable and stable, flip precedence so GUI wins and env becomes a pure bootstrap seed.
4. **Deprecation:** announce, then remove env reads per setting. End state: no env config required or consulted except the single master secret (§5).

Each step is per-setting, so the transition is incremental and reversible.

## 7. Near-term: SAB-lane unification (folds in the agreed quick wins)

Independent of the larger config rework, three concrete frictions block "understandable GUI" today and should land first (they need no secret-storage work):

1. **Backend lane as a first-class Sources card.** The live ADR-0014 Mintarr-managed SAB download lane (`MINTARR_SAB_BACKEND_ENABLED`) has no Sources card — it shows only under System + the new Backend jobs panel — while the *disabled* `sab_usenet` completed-folder connector is prominent. Inverted visibility. Fold the backend lane into the connector readiness model so "what is running" appears where operators look.
2. **Disambiguate the two SABnzbd concepts.** Rename for clarity, e.g. *"SABnzbd — Mintarr-managed download client (recommended)"* vs *"SABnzbd — watch completed folder (passive)"*, with one-line "which do I want?" guidance and a mutual-exclusion hint.
3. **Onboarding parity.** The backend lane is absent from `docker-compose.example.yml` and onboarding docs while the older completed-folder mode is documented. Add it, plus the Lidarr-side wiring steps.

**Do we need the completed-folder mode given the backend lane?** Keep it, but demote it. The two are not redundant — they are different couplings:

| | Completed Folder (`sab_usenet`) | Backend lane (`MINTARR_SAB_BACKEND`) |
|---|---|---|
| Role | passive folder watcher | active download client |
| Flow | Lidarr→SAB→folder→Mintarr ingests | Lidarr→Mintarr→SAB→Mintarr→Lidarr import |
| Coupling | loose | tight (cancel, album-target, durable state) |
| Provenance | inferred from folder contents | full (tied to the Lidarr grab/album) |
| Risk | low (outside critical path) | higher (in critical path) |

For the pre-import QC-gate vision the backend lane is the strategic primary path; completed-folder remains a valid fallback for users who keep SAB as Lidarr's direct client or run non-Lidarr flows. Demote, do not delete — and revisit deletion only once the backend lane is fully mature (qBit backend is not yet built).

## 8. Staged delivery

| Slice | Scope | Depends on |
|---|---|---|
| **F4.6a** | SAB-lane unification §7 (visibility + naming) — no secret storage | none |
| **F4.6b** | Onboarding parity §7.3 (compose + docs) | none |
| **F4.6c** | Non-secret GUI config (URLs/paths/tunables) + bootstrap import §4, §6.1-2 | F4.3 |
| **F4.6d** | Secret store §5 + write-only secret fields §3 | F4.6c |
| **F4.6e** | GUI-primary precedence + env deprecation per setting §6.3-4 | F4.6c/d |
| **F4.6f** | First-run setup surface + Lidarr-wiring guidance §2 | F4.6c-e |

**Build gate.** F4.6a/b may be built directly from this design — they only re-shape connector visibility, naming, and onboarding docs, and touch no secret or write-config surface. **F4.6c-f must not be implemented until a formal ADR is accepted first.** They introduce stored, GUI-writable connection config and an at-rest secret store, which modifies the locked [SECURITY_MODEL.md](../architecture/SECURITY_MODEL.md) invariant *"secrets never browser-visible"* and the env-driven assumption baked into the Phase 0 specs. Per the roadmap's documentation discipline, overriding a locked decision requires an ADR, not just a design doc — see §10.4. This design doc records the proposed shape; the ADR is what authorizes building it.

## 9. Security considerations

- Write-config via web UI is a larger attack surface than read-only env. All config writes are API-key gated like existing dashboard writes, audited via `log_action`, and never echo secrets.
- Master secret (§5) is the one irreducible env/file config; everything else migrates to GUI.
- This does **not** reopen [dynamic third-party plugin loading from UI](../design/CONNECTOR_PLUGIN_ARCHITECTURE.md) (still rejected) — F4.6 configures the *static* registry, it does not load code.

## 10. Open questions

1. Master-secret delivery: env var vs mounted key file vs generated-on-first-boot-and-persisted? (Leaning: generate + persist to a mounted config path, with env override.)
2. Do we expose a read-only "effective config" view that shows non-secret resolved values + secret *presence*, for support/debugging?
3. Lidarr-side wiring: how far does in-app guidance go — a copy-paste checklist with generated URL/key/category, or eventually an API-driven "configure my Lidarr" action (larger blast radius, separate ADR)?
4. **Resolved (this revision):** GUI-native config *does* require a formal ADR before F4.6c-f are implemented, because it overrides the locked "secrets never browser-visible" wording and the env-driven assumption baked into Phase 0 specs (see §8 build gate). Open sub-question: one ADR covering the whole secret/config shift, or split (secret-store ADR vs env-deprecation ADR)?
