# F3.2/F3.3 Newznab Routing Design

> **Type:** Migrated design and implementation record.
> **Status:** Implemented.
> **Version:** 1.0 - 2026-06-03.
> **Scope:** Multi-adapter Newznab search, source-aware NZB pointers, and SAB addurl routing.

This document is the public Mintarr migration of the legacy F3.2/F3.3 routing
design. It removes obsolete private planning references and reflects the
implemented Mintarr contracts.

## 1. Problem

Lidarr has two separate interactions with Mintarr:

1. It searches Mintarr as a Newznab indexer.
2. It grabs one selected result through the SAB-compatible download client.

Once Mintarr has more than one source, the grab must route back to the exact
adapter and candidate that produced the Newznab item. A TIDAL album id, a local
relative path, and a Soulseek completed-folder path cannot share one parser.

## 2. Goals

- Aggregate candidates from all enabled source adapters.
- Emit stable Newznab GUIDs across sources.
- Preserve the exact `source_type` and `source_id` selected by Lidarr.
- Generate a source-aware NZB pointer.
- Decode that pointer during SAB `addurl`.
- Enqueue the correct worker job type.
- Keep Lidarr quality parsing intact.

## 3. Non-goals

- No source-specific verification policy in Newznab routing.
- No dashboard configuration work in F3.2/F3.3.
- No management of Lidarr Custom Formats.
- No reliance on private source paths or credentials in emitted XML.

## 4. Search Aggregation

`GET /api` with Newznab search parameters asks the adapter registry for enabled
sources. Each source returns `ReleaseCandidate` objects.

Mintarr then emits one Newznab item per candidate:

- `<guid>` is `source_type:source_id`.
- title is adapter-provided and must remain Lidarr-parseable.
- source tags such as `[TIDAL]`, `[Local]`, and `[Soulseek]` are allowed only
  after parser regression tests.
- size and quality metadata come from the candidate.
- the `enclosure` URL points to Mintarr's source-aware NZB endpoint.

If one adapter fails, search should still return surviving candidates from the
other enabled adapters.

## 5. Source-Aware Download Endpoint

The Newznab item points to:

```text
/download/<source>/<base64url-source-id>.nzb
```

The `source_id` is base64url encoded so local and Soulseek relative paths can
contain slashes and spaces without becoming route segments or unsafe filenames.

Endpoint behavior:

1. Validate the API key.
2. Decode the base64url source id.
3. Find the adapter by source.
4. Canonicalize the decoded candidate id through the adapter.
5. Emit a minimal NZB pointer containing structured source metadata.

Bad source names, invalid encoding, path traversal, and invalid candidate ids
return `400`/`404` rather than being echoed into headers or filenames.

## 6. NZB Pointer Contract

Mintarr emits a minimal NZB that Lidarr posts back to the SAB-compatible
`addurl` endpoint. The NZB is not a real Usenet download. It is a pointer that
preserves Mintarr source metadata through Lidarr's existing grab path.

The current wire metadata names are intentionally legacy:

```xml
<meta type="tidalhires_source">local</meta>
<meta type="tidalhires_source_id">Artist/Album</meta>
```

Public code should treat those as compatibility field names, not current
branding. The persisted Mintarr fields are `source_type` and `source_id`.

## 7. SAB addurl Routing

When Lidarr posts the NZB back to Mintarr, `addurl` parses source metadata and
selects the adapter:

| Source | Candidate id shape | Job type | Dedupe key |
|---|---|---|---|
| `tidal` | integer album id | `tidal_grab` | `tidal:<album-id>` |
| `local` | normalized relative path | `local_grab` | `local:<path-hash>` |
| `soulseek` | normalized relative path | `soulseek_grab` | `soulseek:<path-hash>` |

The job payload contains `source_id` and safe display metadata. TIDAL jobs can
also carry legacy `album_id` for compatibility.

## 8. Canonicalization

Every adapter can validate and canonicalize candidate ids before enqueue:

- TIDAL validates integer-shaped album ids.
- LocalFolder resolves a relative path under `LOCAL_INGEST_PATH` and rejects
  symlinks, absolute paths, traversal, and non-directories.
- Soulseek validates the completed/downloaded relative path according to its
  adapter contract.

Canonicalization happens both before NZB generation and before job enqueue.
This keeps unsafe text out of headers, filenames, and queue payloads.

## 9. Priority and Custom Formats

Mintarr exposes source tags in release titles so operators can score sources in
Lidarr Custom Formats if they want source preference.

Example policy shape:

| Tag | Typical use |
|---|---|
| `[TIDAL]` | Prefer official TIDAL source when quality is high enough. |
| `[Local]` | Prefer local curated files over remote search when present. |
| `[Soulseek]` | Use community source candidates with stricter review policy. |

Mintarr does not write Lidarr Custom Format configuration. It only emits stable
release titles that make operator-managed rules possible.

## 10. Failure Isolation

Search aggregation must tolerate partial failures:

- one adapter error is logged
- other adapters still return candidates
- malformed candidate ids are rejected before reaching Lidarr
- malformed returned XML is covered by tests
- the worker queue remains source-aware after enqueue

## 11. Security Invariants

- API keys are validated but never printed in public examples.
- Source ids are XML-escaped in NZB pointers.
- Source ids are not used directly in `Content-Disposition`.
- Local path source ids are canonicalized by the adapter.
- NZB pointer metadata is structured, not parsed from free-form titles.
- The addurl path must not infer source from a title regex when metadata is
  present.

## 12. Tests

Required coverage:

- Newznab XML contains candidates from multiple adapters.
- GUIDs include source type and source id.
- Newznab item URLs point to `/download/<source>/<encoded>.nzb`.
- Download endpoint rejects bad base64url source ids.
- Download endpoint rejects unsafe local paths.
- Pointer NZB includes structured source metadata.
- `addurl` enqueues the correct job type and source fields.
- Dedupe does not collapse different sources.
- Release titles still satisfy Lidarr quality parsing expectations.
- Adapter failures do not suppress successful adapters.

## 13. Implementation Record

F3.2/F3.3 landed the key multi-source routing behavior:

- Newznab search aggregates enabled adapter candidates.
- `ReleaseCandidate.guid` is `source_type:source_id`.
- Source-aware callback URLs use base64url-encoded candidate ids.
- SAB `addurl` parses structured source metadata.
- Queue jobs persist `source_type` and `source_id`.
- LocalFolder search results became visible to Lidarr.
- The same route shape later supported Soulseek.
