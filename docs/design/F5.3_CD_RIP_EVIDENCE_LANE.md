# F5.3 — CD-rip evidence lane design

> **Type:** Design
> **Status:** Proposed
> **Owner:** Mintarr maintainers
> **Related:** [Quality stack roadmap §2, §5.4](QUALITY_STACK_ROADMAP.md), [ADR-0012 QC import-gate scope](../architecture/adr/0012-qc-import-gate-scope.md), [ADR-0013 release-family identity policy](../architecture/adr/0013-release-family-identity-policy.md), [F4.5 optional verifier connectors](F4.5_OPTIONAL_VERIFIER_CONNECTORS.md)

## 1. Problem

For complete CD rips, the strongest authenticity proof is not spectral analysis
— it is whether the rip matches known per-disc checksum evidence (EAC/XLD rip
logs, `.cue` sheets, AccurateRip results, CTDB). The [quality stack
roadmap §5.4](QUALITY_STACK_ROADMAP.md) already locks the *policy intent* for
this lane:

| Situation | Policy role |
|---|---|
| AR/CTDB-verified complete CD rip | strong **positive** evidence |
| AR/CTDB no match | no bonus; **not** BLOCK |
| AR/CTDB mismatch with a complete CUE/log | REVIEW_REQUIRED |
| no CUE/log present | skip the CD-rip lane (or treat as low confidence) |

What is missing is the **operational design**: how Mintarr recognises a CD-rip
completed folder, what it reads, how that becomes a `SensorResult`, and how the
lane rolls out without destabilising the existing two-axis policy. This doc
fills that gap and slices the work. The `cd_rip` lane and the `source_specific`
stage already exist in `app/sensor_registry.py` but no sensor occupies them yet.

## 2. Decision

Add a **read-only, evidence-first** CD-rip sensor that parses rip artifacts
already present in the completed folder, emits a standard `SensorResult`, and is
**advisory-only at first** (no score or decision impact). Network-backed
AccurateRip/CTDB verification and any score contribution are gated behind later,
default-off slices.

Two capabilities, deliberately separated:

1. **`cd_rip_evidence` (local, no network):** detect the lane and parse the
   on-disk rip log + `.cue` for self-contained authenticity signals (per-track
   "Copy OK"/CRC status, embedded AccurateRip confidences, TOC/gaps). No
   external binary, no network.
2. **`ctdb` (network, optional, default-off):** later slice — cross-check the
   rip against CTDB/AccurateRip online. A `source_specific_proof` verifier
   connector that starts disabled / `dry_run`, consistent with
   [F4.5](F4.5_OPTIONAL_VERIFIER_CONNECTORS.md).

This doc specifies (1) in full and scopes (2) as follow-up.

## 3. Lane detection

A completed-folder grab is treated as a CD-rip candidate when the grabbed
directory contains rip artifacts, **independent of which completed-folder
connector delivered it** (CD rips arrive via torrent/usenet/Soulseek completed
folders — consistent with [ADR-0012](../architecture/adr/0012-qc-import-gate-scope.md):
Mintarr gates operator-routed completed folders, it does not classify download
clients).

Detection signals, in order of strength:

1. A rip log: a `.log` whose header matches a known ripper
   (`Exact Audio Copy`, `X Lossless Decoder`, `whipper`, `cyanrip`).
2. A `.cue` sheet alongside the audio.
3. Track filenames/TOC consistent with a single-disc rip.

If no rip log **and** no `.cue` are present, the lane is **skipped** (status
`skipped`) — Mintarr does not guess. Detection never changes audio-gate
behaviour; it only decides whether to emit CD-rip evidence.

## 4. `cd_rip_evidence` sensor

Registered as:

```python
SensorDefinition(
    name="cd_rip_evidence",
    sensor_class="source_specific_proof",
    stage="source_specific",
    enabled=True,          # advisory-only; see §6 for why this is safe
    required=False,
    timeout_sec=30,
    fail_policy="skip",     # absence/parse-failure is never a blocker
    applies_to=("usenet", "torrent", "soulseek", "cd_rip"),
)
```

Runtime behaviour (read-only):

- Locate and parse the rip log (best-effort, encoding-tolerant). Extract:
  ripper name + version, per-track test/copy CRC status, AccurateRip result
  lines (confidence + matched/total), and whether the log claims an
  all-tracks-accurate result.
- Detect `.cue` presence and that it references the present audio files.
- Never read or decode audio for this sensor (that is ffprobe/flac_t/Detective).
- Emit a `SensorResult` per the [§2.1 contract](QUALITY_STACK_ROADMAP.md):
  - `class="source_specific_proof"`, `name="cd_rip_evidence"`.
  - `status`: `pass` (log present and self-consistent: tracks "Copy OK" /
    AccurateRip-accurate), `warn` (log present but mismatch / partial /
    inconsistent), `skipped` (no rip log and no cue).
  - `severity`: `info` (or `warning` for a mismatch) — **never `blocker`** in
    this slice.
  - `confidence`: scoped to the lane (log self-consistency / AR confidence),
    never a universal authenticity claim ([§2.2](QUALITY_STACK_ROADMAP.md)).
  - `evidence`: `{ripper, ripper_version, tracks_total, tracks_copy_ok,
    accuraterip: {accurate, confidence, matched, total}, has_cue,
    log_filename}`.

Secret-safety: log content can include local paths and personal directory
names. The sensor stores parsed *fields* (status, counts, confidences), not raw
log text, and never logs full paths — only the log basename, mirroring the
restore status redaction and F4.4 guidance.

## 5. Policy mapping (deferred to a scoring slice)

Slice 1 is advisory-only: the `SensorResult` is persisted in the sidecar and
shown in the dashboard drawer, but the score and the two-axis decision are
unchanged. A later slice wires it into policy exactly per
[§5.4](QUALITY_STACK_ROADMAP.md):

- verified complete rip → positive evidence (audio axis may move
  REVIEW→ACCEPT_PROVISIONAL for the CD-rip lane only; never overrides a hard
  gate or an identity `WRONG_ALBUM`);
- mismatch with a complete log → `REVIEW_REQUIRED`;
- no match / no log → no change.

Keeping scoring out of slice 1 means the lane cannot regress existing decisions
while the parser earns trust on real data — the same read-only-evidence-first
rollout used for F5.1 tag evidence and mandated by
[§2.3](QUALITY_STACK_ROADMAP.md) ("read-only prepass first").

## 6. Why advisory-default-enabled is safe

`enabled=True` is acceptable here — unlike the network/optional `ctdb` sensor —
because the sensor is local, read-only, `fail_policy="skip"`, emits at most
`severity=warning`, and contributes nothing to the score in slice 1. The worst
case is an extra evidence object in the sidecar. CTDB (network, can BLOCK trust
decisions, dependency-bound) stays default-off per
[F4.5](F4.5_OPTIONAL_VERIFIER_CONNECTORS.md) and
[§2.3 budgets](QUALITY_STACK_ROADMAP.md).

## 7. Test plan

- Detection: EAC log, XLD log, whipper log, `.cue`-only, and a non-rip folder
  (→ `skipped`) are each classified correctly.
- Parsing: a known-good EAC log → `pass`, all tracks Copy OK, AccurateRip
  accurate; a tampered/partial log → `warn` with the mismatch surfaced.
- Encoding tolerance: UTF-16/Latin-1 logs parse without raising.
- Read-only: the sensor never opens audio files and never mutates the folder.
- Secret-safety: emitted evidence + logs contain no full paths or raw log text.
- Contract: the emitted `SensorResult` validates against the sensor-result
  schema and round-trips through the sidecar.
- Policy unchanged (slice 1): a record with CD-rip evidence gets the same
  derived status/decision it would without the sensor.

## 8. Non-goals

- No CTDB/AccurateRip **network** calls in slice 1 (separate default-off slice).
- No score/decision change in slice 1 (separate slice, behind evidence).
- No audio decoding in this sensor (that is the existing hard gates / Detective).
- No tag writing or library reorganisation ([ADR-0008](../architecture/adr/0008-strategic-positioning.md) boundary).
- No new download-client management ([ADR-0012](../architecture/adr/0012-qc-import-gate-scope.md)).

## 9. Implementation slices

1. **Pure rip-log/cue parser + detection** (`app/cd_rip_evidence.py`) + unit
   tests. No pipeline wiring. Returns a structured evidence dict.
2. **Register `cd_rip_evidence` sensor + emit advisory `SensorResult`** into the
   sidecar from the verification path; surface it in the dashboard drawer.
   Decisions unchanged.
3. **Policy integration** (behind evidence + opt-in): wire CD-rip evidence into
   two-axis scoring per §5.4. *(Shipped — `MINTARR_CD_RIP_SCORING`.)*
4. **Optional CTDB/AccurateRip verifier connector** (network, default-off,
   `dry_run`), emitting a `ctdb` `SensorResult` — designed separately in
   [F5.3B CTDB network verifier](F5.3B_CTDB_NETWORK_VERIFIER.md).
