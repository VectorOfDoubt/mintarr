# Mintarr — Glossary

> **Type:** Strategy / reference
> **Version:** 1.0 — 2026-05-26
> **Status:** Living document — terms added as the project introduces them.
> **Audience:** Anyone reading Mintarr documentation or code who hits an unfamiliar term.

---

## How to read this

Terms are grouped by domain so related concepts stay next to each other. Within a group, terms are listed in dependency order — definitions referenced by other definitions come first.

When a term has a stricter or more specific meaning in Mintarr than its general English usage, that is called out explicitly. When a term comes from the broader arr-stack ecosystem and Mintarr uses it identically, that is noted with "(arr-stack)".

If you encounter a term in Mintarr code or docs that is not in this glossary, the glossary is incomplete and that is a documentation bug — please open an issue.

## Core abstractions

**Adapter**
A Python code contract used by the Mintarr pipeline. Specifically: `SourceAdapter` (provides files), `VerifierAdapter` (produces evidence), `OutputAdapter` (delivers to a target). Adapters are versioned via SemVer-named Protocol modules (`ADAPTER_PROTOCOL_v1.md`). Compare with Connector.

**Connector**
The operator-facing wrapper around an Adapter (or sometimes around a tool with no adapter, like ffprobe). A Connector adds a manifest, install / config metadata, runtime health and dashboard surface to the underlying Adapter. Static at v1 (registered in code), not dynamically loaded. See [Connector architecture](../design/CONNECTOR_PLUGIN_ARCHITECTURE.md) and [ADR-0003](../architecture/adr/0003-connector-vs-adapter.md).

**Source / Source Connector**
Where audio files come from. TIDAL, LocalFolder, Soulseek, future SAB/qBit/CD-rip/YouTube. Owns the "where do the files originate" question and nothing else.

**Verifier / Verifier Connector**
A tool that produces evidence about audio files. ffprobe (codec inspection), `flac -t` (FLAC integrity), FLAC Detective (spectral analysis), future CUETools/CTDB (CD-rip authenticity), future beets/Picard/AcoustID (metadata identity). Verifier output is evidence, not decisions — the policy turns evidence into decisions.

**Output / Output Connector**
The final delivery target. Lidarr ManualImport today; Plex / Jellyfin / Roon / filesystem-only as Phase 6 lands. An import can target multiple outputs.

**Pipeline**
The fixed four-phase flow every import follows: `download_raw` → `normalize_audio` → `verify` → `import_to_lidarr`. Phase boundaries are explicit; phase invariants are spec'd in [PIPELINE.md](../architecture/PIPELINE.md). Source Adapters own phase 1; the rest is common code.

**Policy**
The Mintarr rules that turn verifier evidence into a verification decision. Encoded in `verification.py`. Versioned (current is V2). Source-agnostic by default; per-source overrides are explicitly out of scope until evidence justifies them.

## Pipeline mechanics

**jid (Job ID)**
A 12-character hex string identifying one import attempt. Used as primary key in `state_db`, in sidecar filenames, in dashboard URLs, in log messages. Generated by Mintarr; not derived from source metadata.

**source_type**
String identifying the source family for a record (`"tidal"`, `"local"`, `"soulseek"`, future `"sab"`, `"qbit"`, `"cd_rip"`, `"youtube"`). Persisted in `state_db.records`, `state_db.jobs`, and sidecar. Used by dashboard filtering and source-aware policy when it lands. Absent on legacy records means "tidal" by default.

**source_id**
String identifying *which* item within a source. For TIDAL, this is the integer album ID as a string. For LocalFolder and Soulseek, this is a normalized POSIX relative path. For future sources, each adapter defines its own form. Combined with `source_type` to form the globally unique `guid`.

**guid**
`f"{source_type}:{source_id}"`. Globally unique identifier for a release candidate across all sources. Used as Newznab `<guid>` value, dedupe key prefix, and audit trail correlation.

**dedupe_key**
The string Mintarr uses to identify "this same job has already been submitted". Format is `f"{source_type}:{hash_or_id}"`. Two job submissions with the same dedupe_key collapse to a single job. Different sources of the same album produce different dedupe_keys deliberately.

**RawDownload**
The dataclass returned by `adapter.download_raw()`. Contains `files_dir`, `file_count`, `total_bytes`. Marks the boundary between "source has produced files" and "common pipeline takes over".

**ReleaseCandidate**
The dataclass adapters return from `search()`. Used to build Newznab XML so Lidarr can decide to grab it. Carries `source_type`, `source_id`, `title`, `artist`, `album`, `year`, `quality_tag`, `size_bytes`, `download_url`, `priority`. Title contract requires Lidarr's quality parser to still detect FLAC/24bit/etc correctly.

**PipelineContext**
The dependency-injection handle Mintarr passes to adapters. Exposes `check_cancelled`, `run_subprocess`, `set_progress`, `log`, `raw_dir`, `output_dir`. Adapters depend only on this Protocol; they do not import from `server.py`.

## Verification and decisions

**V2 verification**
The current generation of Mintarr's verification policy. Replaces an earlier ad-hoc logic. Spec lives in `verification.py` and is dogfooded through every grab. Identified explicitly because future "V3 verification" will be a separate, side-by-side policy with a migration path.

**Verification decision**
One of four outcomes the policy can produce for an import attempt:

- **ACCEPT** — all evidence supports authenticity, import proceeds
- **ACCEPT_PROVISIONAL** — some evidence is mixed, import proceeds with a warning recorded in the sidecar
- **REVIEW_REQUIRED** — evidence is conflicting; the import is held for operator decision
- **BLOCK** — evidence indicates the source is not what it claims to be (fake high-resolution, codec mismatch, etc.); import is rejected and the file is removed

**Import outcome**
The result of the actual import attempt after the verification decision allowed it. One of:

- **MANUAL_IMPORTED** — Lidarr's ManualImport API accepted the files
- **RESCUED** — ManualImport failed; place-files-and-rescan succeeded
- **FAILED** — both ManualImport and rescue failed
- **PENDING** — Lidarr accepted the import as a long-running command and Mintarr stopped waiting
- **SKIPPED** — verification BLOCK prevented import from being attempted

Verification decision and import outcome are independent. A REVIEW_REQUIRED decision has no import outcome until the operator promotes it.

**Sidecar**
A `verification.json` file written next to each imported album in `OUTPUT_BASE/<jid>/`. Contains the full evidence trail, V2 score components, the verification decision, lifecycle state, source_type, and timings. Sidecars are the source of truth for record state; `state_db` is an index over them.

**decisions.jsonl**
An append-only JSON-Lines log under `/config/decisions.jsonl`. One line per verification decision, with redundant data for forensic queries. Not the source of truth — sidecars are — but cheap to grep and survives sidecar deletion.

**REVIEW_REQUIRED workflow**
The operator-facing queue of items the policy could not auto-decide. Surfaced on the dashboard. The operator can `promote` (treat as ACCEPT and run import), `discard` (reject and move sidecar to discarded archive), or wait. Auto-expires after a configurable retention period.

**Lifecycle state**
The current state of a record's existence. One of `created` / `pending_review` / `promoted` / `discarded` / `expired`. Stored in sidecar `lifecycle.state` and indexed in `state_db.records.lifecycle_state`.

## Sources and Lidarr coupling

**Newznab**
A torrent-and-Usenet indexer protocol. Mintarr exposes itself to Lidarr as a Newznab indexer at `GET /api?t=search&q=...`. Lidarr searches for releases; Mintarr returns aggregated `ReleaseCandidate`s from all enabled source adapters.

**SAB compatibility**
Mintarr exposes itself to Lidarr as a SAB-compatible download client at `GET/POST /sabnzbd/api?mode=...`. Lidarr grabs a release; Mintarr accepts the addurl call, enqueues a worker job, and reports status back through SAB-style queue/history.

**addurl**
The SAB protocol mode used to start a grab. Lidarr POSTs `mode=addurl&name=tidal:12345`. Mintarr parses the name prefix to determine which source adapter handles the grab.

**ManualImport**
Lidarr's API endpoint for importing files that arrived through a download client. Mintarr does not use Lidarr's auto-import; it calls ManualImport directly with verified files so V2 policy decisions are honoured.

**rescue / place-files-and-rescan**
A fallback import path Mintarr uses when ManualImport fails (typically due to Lidarr's 80% match bug on edition variants). Files are placed directly in the library folder and a Lidarr rescan is triggered. Logged as `RESCUED` in the import outcome.

**Release-family matching**
The Phase 5.1 feature for handling multi-album / edition / deluxe / remaster / anniversary variants. Mintarr-side mitigation for a Lidarr matching weakness. Not Lidarr code; Mintarr's pre-import release-switch and release-scoring logic.

## Quality terminology

**Hard gate**
A verifier whose failure causes BLOCK regardless of other evidence. Currently `ffprobe` codec detection and `flac -t` integrity check. By definition cannot be disabled while a source is in import mode.

**Codec gate**
The ffprobe check that rejects AAC-in-MP4 files mislabelled as FLAC (a common pattern in transcoded sources). Implemented in `normalize_audio` phase per [PIPELINE.md](../architecture/PIPELINE.md).

**Spectral heuristic**
A verifier that produces a confidence-scored verdict about audio authenticity. FLAC Detective is the canonical example: it inspects the spectral cutoff to detect upsampled MP3-into-FLAC files. Output is `AUTHENTIC` / `WARNING` / `SUSPICIOUS` / `FAKE_CERTAIN` with confidence and per-file detail.

**Provenance**
The trust level Mintarr attaches to a source. TIDAL and CD-rips have high provenance; LocalFolder has medium (depends on operator discipline); Soulseek has low (peer-supplied). Provenance is *context* in the sidecar, not policy by itself. Source-aware policy is Phase 5.2 work.

**dry_run mode**
A verifier connector mode in which evidence is collected and surfaced on the dashboard but does not affect the verification decision. Used for new or experimental verifiers (e.g., beets/Picard/AcoustID first introduction). Hard gates cannot run in `dry_run` while a source is in `import` mode.

## Operator surface

**Dashboard**
The Mintarr web UI. Phase 2 redesigns it to use an arr-stack-style sidebar layout. Today it is a single-page records list with detail drawer.

**Drawer**
The detail panel that opens when a record is clicked on the dashboard. Shows sidecar contents, per-file evidence, verification decision reasoning, available actions.

**Action**
An operator-initiated state change on a record. `promote`, `discard`, `retry_import`, `cancel`. Recorded in `state_db.actions` with actor and timestamp. Actions are auditable.

**Worker queue**
The Mintarr-internal job execution system. SQLite-backed (no Redis / Celery). One worker thread by default (N=1). Worker plucks jobs by type, runs the pipeline, records terminal state. Full F2 worker-queue design doc planned for v0.2.0 migration.

**state_db**
The SQLite database at `/config/mintarr_state.db` (legacy: `tidalhires_state.db`). Indexes sidecar evidence for fast dashboard queries. Five tables: `records`, `sensor_runs`, `file_evidence`, `actions`, `jobs`. Not the source of truth for records — sidecars are. Schema is documented in [DATA_MODEL.md](../architecture/DATA_MODEL.md).

## Project / governance

**ADR (Architecture Decision Record)**
A short document recording a locked architectural decision, why it was made, what was considered, and what triggers a re-evaluation. Numbered (`0001`, `0002`, ...) and append-only — superseded by a new ADR, never edited after lock. Located under `docs/architecture/adr/`.

**P0 / P1 / P2**
Documentation and feature priority tiers. P0 blocks Phase 0 (foundation). P1 blocks first community release. P2 is post-V1.0. Used in the [Documentation Index](../MINTARR_DOCUMENTATION_INDEX.md) and roadmap.

**Foundation phase / Phase 0**
The Mintarr-specific term for the period in which the open-source foundation is established (rename, license decision, public repo, P0 docs, CI). Distinct from V2 verification's "foundation" or any other use of the word.

**Locked decision**
A decision that has been written down in an ADR and is durable until a re-evaluation trigger fires. Contributors cannot get a locked decision changed by adding the feature incrementally; they must propose a successor ADR.

**Boundary test**
The 4-step rule from [ADR-0008](../architecture/adr/0008-strategic-positioning.md) for accepting or rejecting feature proposals. Run before merging any non-trivial feature.

**Boundary**
The line between what Mintarr owns and what Lidarr owns. Defined in ADR-0008. Crossing the boundary is the default scope-rejection criterion.

## arr-stack ecosystem (general usage)

These come from the broader arr-stack community and Mintarr uses them identically. Listed for newcomers from outside the ecosystem.

**arr-stack** (arr-stack)
The family of related self-hosted media manager applications: Sonarr (TV), Radarr (films), Lidarr (music), Readarr (books), Prowlarr (indexer aggregation), Bazarr (subtitles). Share architectural conventions (UI, API, indexer protocols). Mintarr is built for compatibility with this family but is not formally part of it.

**Custom Format (CF)** (arr-stack)
A scoring rule operators configure in Lidarr to influence release selection. Mintarr recommends operators create per-source CFs (`TidalHires-grab` +50, `Local-grab` +20, etc.) but does not manage them programmatically.

**Quality Profile** (arr-stack)
A Lidarr concept defining acceptable quality levels and cutoffs for a series or album. Mintarr does not configure quality profiles — that is Lidarr's job — but Mintarr's V2 decisions interact with Lidarr's `upgradeAllowed` flag.

**Indexer** (arr-stack)
A search source for releases (Usenet groups, public/private torrent trackers, Newznab aggregators). Mintarr exposes itself as a Newznab indexer.

**Download Client** (arr-stack)
A program that fetches files (SABnzbd, NZBGet, Transmission, qBittorrent, Deluge). Mintarr exposes itself as a SAB-compatible download client.

**Tag / Custom Format Tag** (arr-stack)
A regex or attribute Lidarr uses to identify release characteristics. Mintarr's release titles include `[TIDAL]` / `[Local]` / `[Soulseek]` so operators can write CFs that match them.

## Migration glossary

These terms appear in legacy documents and code during the migration from `tidalhires` to `mintarr`. They will be removed once Phase 0 is complete.

**tidalhires**
The pre-rename project name. Replaced by `mintarr`. Lives on in legacy file paths during Phase 0 and in git history.

**TidalHires-grab**
The original Custom Format tag for TIDAL-sourced grabs. Renamed to `Mintarr-tidal` or similar in operator-facing examples during Phase 0; legacy installations should be migrated manually.

**TIDAL_DL_NG_CONFIG**
Environment variable pointing to the Radexito `tidal-dl-ng` config directory. The variable name will not be renamed during migration to avoid breaking existing installs.
