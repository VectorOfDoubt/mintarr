# F5.4 — Scan tiers: metadata vs integrity vs spectral

> **Type:** Design
> **Status:** Accepted
> **Owner:** Mintarr maintainers
> **Related:** [F5.4 library evidence index](F5.4_LIBRARY_EVIDENCE_INDEX.md), [F5.4 integrity classification](F5.4_INTEGRITY_CLASSIFICATION.md), [ADR-0008 strategic positioning](../architecture/adr/0008-strategic-positioning.md)

## 1. Problem

The "cheap" library scan is not cheap: per FLAC it runs **ffprobe** (reads only
container headers — kilobytes) **and `flac -t`** (reads + decodes the *entire*
file to verify frame CRCs + MD5). On ~46k files of tens of MB each, `flac -t` is
~1+ TB of reads plus decode CPU per full pass — the dominant cost, I/O-bound on a
NAS mount. Fusing the two means a full-library overview pays the heavy
integrity cost even when the operator only wants to know *what quality is on
disk*.

**The fix is not to verify integrity less because quality matters less.** It is
to **separate what we know quickly from what we have heavily verified, and make
the policy understand the difference.** Unknown integrity stays *unknown* — never
silently treated as "OK".

## 2. Decision: three independent evidence tiers

Each tier is a separate sensor with its own version, freshness, scan mode, and
parallelism. A trackfile row accumulates evidence from whichever tiers have run.

| Tier | Tool | Cost | Tells us |
|---|---|---|---|
| **Metadata** | ffprobe | header reads, no decode | codec, lossless vs lossy, bit depth, sample rate, channels → the **lossless-tier axis** (lossy / redbook / hi-res / mixed) |
| **Integrity** | `flac -t` | full read + decode | `integrity_ok` (decodes) + `checksum_ok` (FLAC MD5) → genuine corruption vs stale MD5 |
| **Spectral** | FLAC Detective | heaviest | `authentic` (genuine lossless vs measured fake) |

The escalation of *certainty* is the point:

- ffprobe can say **"this looks like 24/96 FLAC."**
- only `flac -t` can say **"it decodes correctly"** (and whether its checksum matches).
- only Detective can say **"it is probably genuine lossless, not a fake."**

Each is strictly stronger evidence than the one above; a higher tier never
*replaces* a lower one, it *adds* certainty.

## 3. Evidence-level / known-ness model (the core principle)

Every quality dimension carries an explicit **known** flag. The decision and the
ranking must distinguish *confirmed* from *unknown*, never collapse them:

| Dimension | Known when | Unknown means |
|---|---|---|
| identity | F5.1 release identity ran | not "matches" |
| lossless tier | metadata tier fresh | tier not asserted |
| hard validity (decodes) | integrity tier fresh | **not** "valid" |
| checksum | integrity tier fresh | not "verified" |
| authenticity | spectral tier fresh | **not** "authentic" |
| completeness | Lidarr track stats | not "complete" |

Stored per-row evidence levels surfaced in the register:
`measured metadata` · `integrity verified` · `checksum mismatch` ·
`spectral verified` · `unknown` · `stale`.

## 4. Measurement model & storage

Split `_default_prober` into two callables: an **ffprobe metadata probe** and a
**`flac -t` integrity probe**. `TrackMeasurement` keeps its fields, but
`integrity_ok` / `checksum_ok` are populated **only** by the integrity tier;
after a metadata-only scan they are `None` (unknown), not `True`.

Sensor versions split by tier, each with independent freshness (same
path/size/mtime basis as today, keyed per tier — exactly how spectral already
works):

- `METADATA_SENSOR_VERSION` — guards the codec/tier fields.
- `INTEGRITY_SENSOR_VERSION` — guards `integrity_ok` / `checksum_ok`.
- `SPECTRAL_SENSOR_VERSION` — unchanged.

`is_metadata_row_fresh` / `is_integrity_row_fresh` / `is_spectral_row_fresh`
mirror the existing pattern; the decision-time guard strips any tier whose
evidence is not fresh (as `_decision_spectral_view` already does), so stale
integrity can never drive a decision.

## 5. Scan modes & parallelism

| Mode | Tool | Measures rows where… | Default parallelism |
|---|---|---|---|
| `metadata` | ffprobe | metadata stale/absent | 8 (cap 16) — header reads, light |
| `integrity` | `flac -t` | metadata fresh **and** integrity stale/absent | 4 (cap configurable) — full-file I/O |
| `spectral_missing` | Detective | metadata+integrity fresh, spectral absent/stale | 1 (existing) |

The heavy tiers only ever run on rows the cheaper tier already covered (an
integrity scan needs a fresh metadata row; spectral needs both). Parallelism is
**per tier and explicit** — light metadata can fan out, integrity stays modest
because it is NAS/disk-I/O-bound, spectral stays serial. Start with these fixed
defaults (`MINTARR_LIBRARY_*_SCAN_WORKERS`); dynamic throughput-based tuning is a
later, separate concern. Every tier keeps the slice-5 guarantees: operator-/
scheduler-triggered, import-yield, lease/heartbeat, ledger resume, never blocks
import QC.

**Back-compat / defaults (guardrail).** Today's `cheap` mode is retained only as
a **legacy alias** that runs `metadata` then `integrity`. The **scheduler and the
dashboard/API default must explicitly use `metadata`** — if either keeps
defaulting to `cheap`, the full-library sweep silently keeps paying the `flac -t`
cost and the performance gain disappears. The fast `metadata` pass is the
default sweep; `integrity` is operator-/scheduler-triggered or on-demand.

## 6. Decision policy — conservative on the unknown

`compare()` already abstains on unknown candidate tier (#115) and unverified
existing authenticity (4b). This extends the same discipline to **integrity
known-ness**, per the locked principle *unknown ≠ confirmed-good*:

- A candidate with **confirmed-good integrity** may beat an existing release whose
  integrity is **unknown** (we measured the candidate; we have not verified the
  existing file).
- An existing release with **unknown integrity** must **not auto-block** a
  better-verified candidate — but neither does its unknown state count as a defect
  that *forces* an upgrade (that is the stale-MD5 trap #129 already guards).
- An existing release with **verified-good integrity** is **protected**: a worse
  or unknown-integrity candidate does not replace it.
- When the decision would hinge on an **unknown** integrity/authenticity on either
  side, prefer **REVIEW** over ACCEPT.

This keeps the lexicographic precedence (identity > hard validity > authenticity
> tier > completeness) but adds a *known/unknown* dimension at each axis: an axis
only counts as "passed" when it was actually measured. Default-safe: with the
heavy tiers unmeasured, decisions fall back to today's behaviour and never
upgrade on absence of evidence.

## 7. Ranking view

The register shows each album's evidence level explicitly so the operator sees
*how much we actually know*: `measured metadata` (tier known, integrity unknown),
`integrity verified`, `checksum mismatch`, `spectral verified`, `unknown`,
`stale`. The existing tier buckets (`lossy` / `redbook` / `mixed_tier`) come from
the fast metadata pass; `invalid` / `checksum_mismatch` / `measured_fake` require
their heavier tier and read as *unknown* until it has run — never as `ok`.

**Guardrail — `ok` means verified, not just measured.** A metadata-only album
(tier known, integrity not yet run) must **never** render as the fully-verified
`ok` bucket; that would present *unknown* as *confirmed-good*. The `ok` bucket
requires **integrity verified** (and authenticity verified when spectral is
enabled). A clean metadata-only album instead carries an explicit evidence level
such as `measured metadata · integrity unknown`. Tier is orthogonal to evidence
level: e.g. a row can be bucket `redbook` with level `integrity unknown`, then
later `redbook` + `integrity verified`. The API/UI surfaces both the tier bucket
and the evidence level so "we measured headers" is never confused with "we
verified the audio".

## 8. Migration

`integrity_ok` / `checksum_ok` move from the (fused) cheap sensor to the new
integrity sensor. On rollout, existing rows are re-evaluated per tier: the
metadata fields re-confirm cheaply under `METADATA_SENSOR_VERSION`; integrity
reads `unknown` until an integrity scan runs. No backfill script — the per-tier
freshness checks drive lazy re-measurement, as with every prior sensor bump.

## 9. Implementation slices

1. **Tier-split measurement + storage.** Split the prober; per-tier sensor
   versions + freshness guards; `metadata`/`integrity` scan modes; per-tier
   worker parallelism. Ranking shows evidence levels. No decision change.
2. **Decision policy.** Wire integrity/authenticity known-ness into `compare()`
   (§6), behind the existing `MINTARR_MEASURED_EXISTING` opt-in.
3. **(Later) Dynamic parallelism / throughput tuning** — out of scope here.

## 10. Non-goals

- No reduction in integrity/authenticity rigor — the heavy tiers are unchanged,
  just decoupled and explicitly evidence-levelled.
- No FLAC re-encoding or MD5 rewriting (read-only register; ADR-0008 boundary).
- No dynamic auto-tuning of worker counts in this design (fixed explicit defaults).
- No change to identity ownership: Lidarr owns identity, Mintarr owns quality
  evidence with explicit certainty levels.
